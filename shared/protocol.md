# WebSocket Protocol (Phase 0)

All WebSocket frames are **JSON text messages**.

- **Audio** is sent as base64-encoded raw PCM in JSON (simple and portable). In the future, audio may switch to **binary frames** for efficiency.
- The client generates a **`session_id`** (UUID) and includes it in every message.
- The server is **stateless** at the protocol layer: every message includes `session_id` so messages can be routed/handled without relying on connection-local state.
- Ordering is **best-effort**: messages include a `seq` number, and the protocol allows future `ack`/resend logic even if the MVP skips it.

## General conventions

- `session_id`: string UUID generated by the client.
- `stream_id`: `"mic"` | `"system"` (audio source).
- `seq`: integer sequence number per `(session_id, stream_id)` stream (monotonic increasing).
- `timestamp_ms`: number; client-side timestamp (either epoch ms or monotonic ms). The client should be consistent within a session.

## Client → Server messages

### `audio_chunk`

Send a chunk of audio data.

#### Schema

```json
{
  "type": "audio_chunk",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "stream_id": "mic",
  "seq": 42,
  "timestamp_ms": 1730000000123,
  "audio_format": {
    "encoding": "pcm_s16le",
    "sample_rate_hz": 16000,
    "num_channels": 1
  },
  "audio_base64": "AAABAAIA..." 
}
```

#### Fields

- `type`: `"audio_chunk"`
- `session_id`: string UUID
- `stream_id`: `"mic"` | `"system"`
- `seq`: integer
- `timestamp_ms`: number
- `audio_format.encoding`: `"pcm_s16le"` (raw PCM, signed 16-bit little-endian)
- `audio_format.sample_rate_hz`: number (e.g. `16000`)
- `audio_format.num_channels`: number (MVP expects `1`)
- `audio_base64`: base64 string containing the raw PCM bytes

### `control`

Control messages for lifecycle and metadata (reserved for later phases).

#### Schema

```json
{
  "type": "control",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "command": "metadata",
  "payload": {
    "stream_speakers": {
      "mic": {
        "speaker_id": "local:mic",
        "speaker_label": "You",
        "speaker_source": "manual",
        "speaker_confidence": 0.9
      }
    },
    "participants": [
      { "id": "zoom-user-1", "name": "Taylor" }
    ]
  }
}
```

#### Fields

- `type`: `"control"`
- `session_id`: string UUID
- `command`: `"start"` | `"stop"` | `"ping"` | `"pong"` | `"metadata"` | `"speaker_activity"`
- `payload`: optional object (command-specific)

#### Speaker metadata

- `metadata.payload.participants`: optional participant list for Zoom/RTMS-style speaker IDs.
- `metadata.payload.stream_speakers`: optional fallback labels per audio source.
- `speaker_activity.payload`: optional active-speaker interval, usually for `"system"` audio:

```json
{
  "type": "control",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "command": "speaker_activity",
  "payload": {
    "participant_id": "zoom-user-1",
    "participant_name": "Taylor",
    "stream_id": "system",
    "start_timestamp_ms": 1730000000123,
    "end_timestamp_ms": 1730000002345
  }
}
```

## Server → Client messages

### `transcript_update`

Incremental transcript updates. The client should treat these as **append/replace** updates based on `segments[*].id`, not purely as a stream of text.

#### Schema

```json
{
  "type": "transcript_update",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "segments": [
    {
      "id": "seg-0001",
      "start_sec": 0.0,
      "end_sec": 1.92,
      "text": "hello world",
      "stream_tags": ["mic"],
      "speaker_id": "local:mic",
      "speaker_label": "You",
      "speaker_source": "manual",
      "speaker_confidence": 0.9,
      "is_final": true,
      "full_context_available": true,
      "final_reason": "punctuation"
    }
  ]
}
```

#### Segment fields

- `id`: string (stable identifier for the segment)
- `start_sec`: number
- `end_sec`: number
- `text`: string
- `stream_tags`: array of `"mic"` | `"system"` (may contain one or both)
- `speaker_id`: stable speaker ID when available
- `speaker_label`: display label such as `"You"` or a Zoom participant name
- `speaker_source`: `"stream"` | `"zoom"` | `"diarization"` | `"manual"` | `"unknown"`
- `speaker_confidence`: number from `0.0` to `1.0`
- `is_final`: boolean
  - `false` = partial/intermediate hypothesis
  - `true` = final segment that should not change (except in rare future corrections)
- `full_context_available`: boolean (reserved for future use)
- `final_reason`: optional string, e.g. `"punctuation"`, `"pause"`, `"speaker_change"`, `"max_duration"`, `"stop"`

### `error`

Structured error message.

#### Schema

```json
{
  "type": "error",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "code": "bad_request",
  "message": "audio_format.sample_rate_hz must be 16000"
}
```

#### Fields

- `type`: `"error"`
- `session_id`: string UUID (echo back if known; otherwise may be omitted in future)
- `code`: string (machine-readable)
- `message`: string (human-readable)

## Future-proofing: `ack` (possible future message)

An explicit acknowledgement message can be added later to support resend and stronger ordering guarantees.

```json
{
  "type": "ack",
  "session_id": "1b0d8f1e-2e8c-4e5f-baf5-0c0f4d1d5c3b",
  "last_seq_received": 42
}
```

Notes:

- `last_seq_received` is the highest contiguous `seq` the server has processed for the relevant stream(s).
- The MVP may skip `ack`; clients should still send `seq` so this can be added later without breaking compatibility.
